Build on the paired replay null result. Intended user task: evaluate an inspected local DRF module against a fixed historical reference, held-out regression class and optional compatibility check, retaining a complete report without modifying the source checkout. Portable scoring/evidence remains separate from Linux execution. No new model calls in this slice.

Allowed writes: benchmarks/drf/, targeted tests/, docs/framework/STATE.md and a manually dispatched CI workflow. Private live evidence under ~/.local/share/proofgate-framework/. Preserve frozen POC and existing services. No merges, deployments, repository settings, auth changes or upstream writes. Bound:20 minutes command execution,512MiB new storage,two CPUs. No new providers or system packages on this home server.

Acceptance: source comes from the pinned git object, candidate substitution affects only the declared module, held-out test file matches its published digest, evaluator code and observations are bound in reports, original/upstream expected behavior is reproduced locally, existing regressions pass, fresh review covers filesystem/resource handling and scoped claims. Unit/mocked CI transport tests remain distinct from actual user-scope runs. Never silently run without namespace or resource controls. Never report skipped/error/empty suites as passing.

CI transport: manual-only shadow experiment, read-only repository token, no deployment secrets, fixed DRF historical cases, evaluator from selected reviewed workflow revision. Candidate process sees neither host home nor credentials nor network. GitHub-hosted transport may use a transient root-created resource scope but must drop to the original runner UID/GID before candidate execution. No root candidate execution. Do not change host security policy to make a failing namespace prerequisite pass. CI activation depends on owner review/merge; do not bypass that approval gate.

This remains an inspected-code diagnostic tool. Same-process Python tests are not resistant to a malicious module that tampers with pytest or its dependencies. Standard libraries and host are trusted and incompletely fingerprinted. The tool supplies no production release authority or formal proof. A future adversarial acceptance runner needs a separate design and failure controls, not an expanded claim about this prototype.
