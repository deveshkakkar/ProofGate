# Check a selected Python boundary in your own checkout

This experimental adapter runs selected, inspected Python files against a reviewed JSON fixture contract. It supports a batch of JSON inputs on stdin and a same-length result list on stdout. It needs the Linux sandbox described in [TRY.md](TRY.md); there is no native macOS/Windows backend or package distribution. It checks finite examples, not arbitrary service correctness. No model, shell-command plugin or requirements generator runs.

You can keep your repository, file names and reviewed fixtures separate from ProofGate. Copy neither your private repository nor secrets into ProofGate. From your own checkout, use the isolated entrypoint in a pinned ProofGate checkout. `-I` excludes your current directory and Python environment overrides from evaluator imports; the source tree is read as data until sandbox execution:

```sh
python3 -I -B /absolute/path/to/ProofGate/scripts/proofgate.py doctor
python3 -I -B /absolute/path/to/ProofGate/scripts/proofgate.py check-json \
  --candidate . \
  --contract /reviewed-policy/contract.json \
  --expected-contract SHA256_FROM_INDEPENDENT_REVIEW \
  --output /your-evidence/new-report.json
```

The pin is the SHA256 of the exact contract file bytes, obtained through your review process. It is not a digest generated by the candidate or automatically accepted alongside a proposed contract. The command checks equality with the supplied pin; **it cannot authenticate who reviewed that pin or enforce policy ownership**. Allowing an agent to change both the contract and the accepted pin defeats independent checking. Reports explicitly retain `producer_authenticated:false`, `policy_admitted:false` and `release_authorized:false`; this command cannot authorize merging/deployment.

## Small contract

```json
{
  "schema": 1,
  "runtime": "python-json-batch-v1",
  "files": ["service.py", "rules/credit.py"],
  "entrypoint": "service.py",
  "assumptions": ["Only these two integer credit examples in a cleared environment are modeled."],
  "checks": [{
    "id": "credit_examples",
    "inputs": [{"balance": 10, "request": 4}, {"balance": 10, "request": 12}],
    "expected": [{"granted": 4, "remaining": 6}, {"granted": 0, "remaining": 10}]
  }]
}
```

`service.py` must read the input list and produce the expected list through the actual business-rule boundary. The adapter always invokes the fixed sandboxed Python interpreter; the contract contains no shell commands or executable oracle. Each named group launches a fresh process with the whole input batch. State between groups/processes is not checked. Use JSON booleans as booleans; `true`, `1` and `1.0` are distinct observations.

The contract allows 1–32 explicitly selected `.py` files, at most 256 KiB each/1 MiB total. Relative paths and their components cannot traverse symlinks. Other checkout files—including `.git`, docs, credentials, unselected dependencies and configuration—are excluded from the worker and coverage. Entrypoint must be selected. Modules must work from the selected tree with the host Python standard library; no third-party dependencies are installed. Dependency packaging, native extensions, network services and alternate environment profiles are unsupported.

There are 1–4 uniquely named check groups, each with 1–256 inputs and the same number of expected outputs. Contract bytes are limited to 256 KiB; duplicate JSON keys and non-finite numbers reject. The existing resource limits (256 MiB address space/memory scope, one CPU, 16 tasks, 5-second scope, 1 MiB output files and 10-second parent timeout per group) remain unchanged. Limits are not an established hostile-source security guarantee. Host libraries are trusted and partially fingerprinted.

Exit 0 means the selected snapshot matches all finite expectations and current selected files still matched at the final observation. Exit 1 means a mismatch. Exit 2 means setup/evaluation failure or observed current-source change. Reports are owner-only, never overwritten, and include fixture/source/evaluator/environment identities, all available observations and explicit assurance limits. Keep failed records and choose a new output path. Postcheck is an observation rather than a lock; PR admission would need independently protected policy/evaluator and an identity check at the merge boundary.

## External integration example

[The python-stdnum example](../../examples/stdnum-json/README.md) selects a pinned real external repository and adds an inspectable JSON shim. It preserves five upstream examples and adds two explicitly declared invalid-input fixtures. The shim and expectations are agent-authored interpretations, not independently approved customer policy. Its deliberately broken checksum is a negative control, not a discovered upstream defect. Source selection/pins and the contract are data; no evaluator edits are needed for another compatible Python boundary.

The workflow is technical integration evidence only. Total specification/adaptation/maintenance effort versus equivalent CI, unfamiliar-developer success and repeat use remain unmeasured. See [VALIDATION-DECISION.md](VALIDATION-DECISION.md) before expanding product claims.
